# Codex Responses 中转站通信协议移植指南

更新日期：`2026-08-11`

适用范围：将本程序的 **Codex 风格 Responses 流式调用**移植到其他服务、桌面程序、脚本或后端服务。

本文是面向移植的上游线协议说明，只描述“你的程序 → 中转站”的 HTTP/SSE 通信。它不要求移植本项目的 Next.js 路由、Key 管理、诊断界面或视频业务逻辑。

> 实现依据：[`src/lib/ai/providers/codex-responses.ts`](../src/lib/ai/providers/codex-responses.ts)。若代码与本文不一致，以该文件和对应测试为准。更完整的本地测试端点、浏览器诊断事件说明见 [Codex API 测试输入输出协议](./Codex%20API%20测试输入输出协议.md)。

## 1. 最小移植结论

一次调用需要完成以下六件事：

1. 将配置的 Base URL 规范化为 `POST /v1/responses`。
2. 使用 `Authorization: Bearer <API_KEY>`，并发送本指南列出的 Codex 风格身份 Header。
3. 发送 Responses JSON：system prompt 放在 `instructions`，用户输入放在 `input`。
4. 固定使用 `stream: true` 与 `store: false`，接受 `text/event-stream`。
5. 按 SSE 的空行分帧，读取 `data:` 行；以 JSON 内的 `type` 判断事件类型。
6. 只拼接 `response.output_text.delta` 的 `delta`，并且**只有收到 `response.completed` 才算成功**。

`data: [DONE]` 可被记录为流已结束的兼容标记，但本程序不会把它单独视为成功；若没有 `response.completed`，应把这次调用判为不完整。

```text
你的程序
  └─ POST <base-url>/v1/responses
       ├─ Headers：Bearer 凭据 + Codex 请求身份
       ├─ Body：Responses JSON（stream=true）
       └─ Response：SSE
            ├─ response.output_text.delta → 追加正文
            ├─ response.completed         → 成功
            └─ response.failed / error    → 失败
```

## 2. 地址规则

配置中保存的是 Base URL，而不是固定完整路径。移植时按以下规则构造最终地址：

| 输入 Base URL | 最终请求地址 |
|---|---|
| `https://relay.example` | `https://relay.example/v1/responses` |
| `https://relay.example/` | `https://relay.example/v1/responses` |
| `https://relay.example/v1` | `https://relay.example/v1/responses` |
| `https://relay.example/v1/` | `https://relay.example/v1/responses` |
| `https://relay.example/v1/responses` | 保持不变 |

请通过 URL 解析库处理路径和查询参数，不要简单字符串拼接。当前实现要求 Base URL 是绝对 URL；无效地址会在发请求前失败。

## 3. HTTP 请求

### 3.1 方法和必须 Header

```http
POST /v1/responses HTTP/1.1
Accept: text/event-stream
Authorization: Bearer <API_KEY>
Content-Type: application/json
Originator: codex_cli_rs
User-Agent: codex_cli_rs/0.0.0 (Windows; x86_64)
Session-Id: <uuid-v4，每次请求新建>
Thread-Id: <uuid-v4，每次请求新建>
X-Client-Request-Id: <同 Thread-Id>
X-Codex-Installation-Id: <uuid-v4，进程生命周期内稳定>
X-Codex-Window-Id: <thread-id>:0
X-Codex-Turn-Metadata: <JSON 字符串，见下文>
```

Header 名不区分大小写，示例中的大小写是便于阅读。本程序每次调用都会生成新的 `session-id`、`thread-id`、`turn-id`；`x-codex-installation-id` 则在进程加载通信模块时生成一次并复用，直到进程重启。

`x-codex-turn-metadata` 的值是**序列化后的单行 JSON 字符串**，而不是嵌套 JSON Header：

```json
{
  "installation_id": "<installation-id>",
  "session_id": "<session-id>",
  "thread_id": "<thread-id>",
  "turn_id": "<turn-id>",
  "window_id": "<thread-id>:0",
  "request_kind": "turn",
  "turn_started_at_unix_ms": 1785893309048
}
```

中转站的实际兼容性由其实现决定。若它不识别这些 Codex 识别 Header，通常仍应忽略未知 Header；移植时不要省略 `Authorization`、`Content-Type`、`Accept`、`model`、`input`、`stream` 等基础字段。

### 3.2 请求体

以下是一次纯文本请求的完整形状。`instructions` 和 `input` 中的文本由调用方替换，其他字段按当前程序固定发送：

```json
{
  "model": "gpt-5.6-terra",
  "instructions": "你是一个有帮助的助手。",
  "input": [
    {
      "type": "message",
      "role": "user",
      "content": [
        { "type": "input_text", "text": "请用一句话说明 RAG。" }
      ]
    }
  ],
  "tools": [],
  "tool_choice": "auto",
  "parallel_tool_calls": false,
  "reasoning": { "effort": "low", "summary": "auto" },
  "store": false,
  "stream": true,
  "include": ["reasoning.encrypted_content"],
  "prompt_cache_key": "<session-id>",
  "text": { "verbosity": "medium" },
  "client_metadata": {
    "x-codex-installation-id": "<installation-id>",
    "session_id": "<session-id>",
    "thread_id": "<thread-id>",
    "turn_id": "<turn-id>",
    "x-codex-window-id": "<thread-id>:0",
    "x-codex-turn-metadata": "<与 Header 相同的 JSON 字符串>"
  }
}
```

### 3.3 消息转换规则

调用方可以传入最多 12 条最近消息；本程序会将每条消息转换为一个 Responses `input` item：

| 原消息角色 | `content` 项 |
|---|---|
| `user`，文本 | `{ "type": "input_text", "text": "..." }` |
| `assistant`，文本 | `{ "type": "output_text", "text": "..." }` |
| `user`，图片 | `{ "type": "input_image", "image_url": "data:image/...;base64,..." }` |

用户消息可同时带文本与图片，顺序固定为文本在前、随后每张图片各一个 `input_image`。助手历史只携带文本，不携带图片。多轮模式每次发送完整的有限历史，**不发送** `previous_response_id`。

图片的实际链路使用 data URL，例如：

```json
{
  "type": "input_image",
  "image_url": "data:image/png;base64,iVBORw0KGgoAAAANSUhEUg..."
}
```

本程序测试入口只接受 PNG、JPEG、WebP、GIF；单条用户消息至多 10 张、单张至多 15 MiB、一次最近 12 条历史的图片原始数据总量至多 60 MiB。其他程序可按自身需求调整限制，但应在请求前验证 MIME、Base64 和字节数，且绝不要把 data URL 写入普通日志。

### 3.4 当前不发送的字段

为保持与当前程序一致，请不要自动附加下列字段：

- `max_output_tokens` 或 `max_tokens`
- `previous_response_id`
- 工具定义、`web_search` 或任意项目私有工具
- Chat Completions 格式的 `messages` 顶层字段

`tools: []` 和 `tool_choice: "auto"` 虽看起来冗余，但它们是当前请求形状的一部分，应保留。

## 4. SSE 响应与成功判定

### 4.1 分帧规则

中转站成功后应返回：

```http
Content-Type: text/event-stream
```

解析规则如下：

1. 允许 `\n\n` 或 `\r\n\r\n` 分隔一个 SSE 块。
2. 一个块可能包含多行 `data:`；移除每行 `data:` 前缀和一个可选空格后，用换行连接，再作为一个整体解析。
3. `data: [DONE]` 是兼容结束标记。
4. 其他 `data:` 内容必须是 JSON 对象。
5. 以对象的 `type` 字段判断事件类型；不要依赖 SSE 的 `event:` 字段。

典型事件顺序：

```text
response.created
response.in_progress
response.output_item.added
response.content_part.added
response.output_text.delta       （重复 0～多次）
response.output_text.done
response.content_part.done
response.output_item.done
response.completed
[DONE]                           （可选）
```

### 4.2 必须消费的事件

| 上游 JSON `type` | 移植程序应做的事 |
|---|---|
| `response.created` | 可记录 `response.id` 和初始 `response.status`。 |
| `response.output_text.delta` | 若 `delta` 是字符串，按到达顺序追加到最终正文。 |
| `response.completed` | 读取 `response.id`、`response.status` 和 `response.usage`；标记成功。 |
| `response.failed` / `error` | 从 `response.error.message`、`message` 或 `error.message` 取错误并失败。 |
| `response.incomplete` | 不能视为成功；若最终没有 `response.completed`，按未完成失败。 |
| 其他事件 | 可保留用于诊断，但不应中断文本输出。常见可选事件包括 reasoning summary。 |

正文只来自 `response.output_text.delta.delta`。不要将 reasoning summary、原始完整事件或 `encrypted_content` 拼入用户可见结果。

一个最小成功事件示例：

```text
data: {"type":"response.output_text.delta","delta":"RAG 是让模型先检索相关资料"}

data: {"type":"response.output_text.delta","delta":"再生成回答的模式。"}

data: {"type":"response.completed","response":{"id":"resp_123","status":"completed","usage":{"input_tokens":42,"output_tokens":21,"total_tokens":63}}}

data: [DONE]

```

最终正文是：`RAG 是让模型先检索相关资料再生成回答的模式。`

### 4.3 结束状态表

| 观察到的情况 | 本程序的判定 | 建议移植行为 |
|---|---|---|
| 收到 `response.completed` 后流结束 | 成功 | 返回拼接后的正文及 usage。 |
| 收到 `[DONE]`，但从未收到 `response.completed` | 失败，`done` | 丢弃/标记本次不完整结果，允许由业务层决定是否重试。 |
| 网络流自然结束，但没有完成事件 | 失败，`eof` | 报告“流在完成事件前结束”。 |
| HTTP 非 2xx | 失败，`failed` | 读取有限长度响应体，优先提取 JSON 的 `error.message`。 |
| `response.failed` 或 `error` | 失败，`failed` | 显示脱敏后的上游错误。 |
| 调用方取消请求 | `aborted` | 取消底层请求，不伪造 `completed`。 |

## 5. 可直接移植的原生 JavaScript 参考实现

以下示例不依赖 OpenAI SDK，使用运行时原生 `fetch` 和 Web Streams。Node.js 18+、现代浏览器 Service Worker、Deno、Bun 等均可据此改造；桌面程序请确保请求在安全的服务端/主进程执行，避免暴露 API Key。

```js
import { randomUUID } from 'node:crypto';

const installationId = randomUUID(); // 每个进程生成一次

function buildResponsesUrl(baseUrl) {
  const url = new URL(baseUrl);
  const path = url.pathname.replace(/\/+$/, '');
  if (/\/responses$/i.test(path)) return url.toString();
  url.pathname = /\/v1$/i.test(path) ? `${path}/responses` : `${path}/v1/responses`;
  return url.toString();
}

export async function callRelay({ baseUrl, apiKey, model, instructions, messages, signal }) {
  const sessionId = randomUUID();
  const threadId = randomUUID();
  const turnId = randomUUID();
  const windowId = `${threadId}:0`;
  const turnMetadata = JSON.stringify({
    installation_id: installationId,
    session_id: sessionId,
    thread_id: threadId,
    turn_id: turnId,
    window_id: windowId,
    request_kind: 'turn',
    turn_started_at_unix_ms: Date.now(),
  });

  const input = messages.slice(-12).map(({ role, content, images = [] }) => ({
    type: 'message',
    role,
    content: role === 'assistant'
      ? [{ type: 'output_text', text: content }]
      : [
          ...(content ? [{ type: 'input_text', text: content }] : []),
          ...images.map(dataUrl => ({ type: 'input_image', image_url: dataUrl })),
        ],
  }));

  const body = {
    model,
    instructions,
    input,
    tools: [],
    tool_choice: 'auto',
    parallel_tool_calls: false,
    reasoning: { effort: 'low', summary: 'auto' },
    store: false,
    stream: true,
    include: ['reasoning.encrypted_content'],
    prompt_cache_key: sessionId,
    text: { verbosity: 'medium' },
    client_metadata: {
      'x-codex-installation-id': installationId,
      session_id: sessionId,
      thread_id: threadId,
      turn_id: turnId,
      'x-codex-window-id': windowId,
      'x-codex-turn-metadata': turnMetadata,
    },
  };

  const response = await fetch(buildResponsesUrl(baseUrl), {
    method: 'POST',
    signal,
    headers: {
      accept: 'text/event-stream',
      authorization: `Bearer ${apiKey}`,
      'content-type': 'application/json',
      originator: 'codex_cli_rs',
      'user-agent': 'codex_cli_rs/0.0.0 (Windows; x86_64)',
      'session-id': sessionId,
      'thread-id': threadId,
      'x-client-request-id': threadId,
      'x-codex-installation-id': installationId,
      'x-codex-window-id': windowId,
      'x-codex-turn-metadata': turnMetadata,
    },
    body: JSON.stringify(body),
  });

  if (!response.ok) throw new Error(`Relay HTTP ${response.status}: ${await response.text()}`);
  if (!response.body) throw new Error('Relay returned an empty response body');

  let output = '';
  let completed;
  const reader = response.body.getReader();
  const decoder = new TextDecoder();
  let buffer = '';

  const consumeBlock = block => {
    const data = block.split('\n')
      .filter(line => line.startsWith('data:'))
      .map(line => line.slice(5).trimStart())
      .join('\n')
      .trim();
    if (!data || data === '[DONE]') return;

    const event = JSON.parse(data);
    if (event.type === 'response.output_text.delta' && typeof event.delta === 'string') {
      output += event.delta;
      // 可选：这里将 event.delta 实时推给你的 UI。
    } else if (event.type === 'response.completed') {
      completed = event.response;
    } else if (event.type === 'response.failed' || event.type === 'error') {
      throw new Error(event.response?.error?.message ?? event.error?.message ?? event.message ?? 'Relay stream failed');
    }
  };

  while (true) {
    const { done, value } = await reader.read();
    buffer += decoder.decode(value, { stream: !done }).replace(/\r\n/g, '\n');
    const blocks = buffer.split('\n\n');
    buffer = blocks.pop() ?? '';
    for (const block of blocks) consumeBlock(block);
    if (done) break;
  }
  if (buffer) consumeBlock(buffer);
  if (!completed) throw new Error('Relay stream ended before response.completed');

  return {
    output,
    responseId: completed.id,
    status: completed.status,
    usage: completed.usage && {
      input: completed.usage.input_tokens,
      output: completed.usage.output_tokens,
      total: completed.usage.total_tokens,
    },
  };
}
```

示例调用：

```js
const result = await callRelay({
  baseUrl: process.env.AI_BASE_URL,
  apiKey: process.env.AI_API_KEY,
  model: 'gpt-5.6-terra',
  instructions: '你是一个简洁、可靠的中文助手。',
  messages: [{ role: 'user', content: '解释什么是 SSE。' }],
});

console.log(result.output);
```

> 示例为了可读性直接将 HTTP 错误文本放进 `Error`。生产代码应限制错误体长度，并清除 API Key、Bearer Token、Cookie、`encrypted_content` 与图片 data URL 后再记录或展示。

## 6. curl 冒烟测试

下例用于验证中转站是否接受最小的流式 Responses 请求。它故意省略了可选的 Codex 身份 Header，便于排障；要做到与本程序字节语义一致，应补齐第 3.1 节 Header 和第 3.2 节 body 字段。

```bash
curl --no-buffer --request POST "$AI_BASE_URL/v1/responses" \
  --header "Authorization: Bearer $AI_API_KEY" \
  --header "Accept: text/event-stream" \
  --header "Content-Type: application/json" \
  --data '{
    "model":"gpt-5.6-terra",
    "instructions":"你是一个有帮助的助手。",
    "input":[{"type":"message","role":"user","content":[{"type":"input_text","text":"回复 pong"}]}],
    "tools":[],
    "tool_choice":"auto",
    "parallel_tool_calls":false,
    "reasoning":{"effort":"low","summary":"auto"},
    "store":false,
    "stream":true,
    "include":["reasoning.encrypted_content"],
    "text":{"verbosity":"medium"}
  }'
```

如果 `AI_BASE_URL` 已经以 `/v1` 结尾，上例正确；如果它已经是完整的 `/v1/responses`，请直接请求该 URL，不要再拼接一次 `/v1/responses`。生产程序应使用第 2 节的地址规范化函数，避免这一类手工错误。

## 7. 移植验收清单

- [ ] Base URL 分别配置为域名根、`/v1/`、`/v1/responses` 时，最终地址均正确。
- [ ] 每次请求生成新的 session/thread/turn UUID，但 installation ID 在同一进程中稳定。
- [ ] 请求使用 `POST`、Bearer 鉴权、`Accept: text/event-stream`、`Content-Type: application/json`。
- [ ] 请求体包含 `stream:true`、`store:false`、`tools:[]`、`tool_choice:"auto"`、`parallel_tool_calls:false`。
- [ ] system prompt 进入 `instructions`，而不是 Chat Completions 的 `messages[0]`。
- [ ] 用户历史编码为 `input_text`，助手历史编码为 `output_text`。
- [ ] 支持 CRLF、分块到达和一个 SSE 块里的多行 `data:`。
- [ ] 只拼接 `response.output_text.delta.delta`。
- [ ] `response.completed` 才返回成功；只有 `[DONE]` 时返回不完整错误。
- [ ] `response.failed`、`error`、非 2xx、非法 JSON 和中途断流都能明确失败。
- [ ] 取消操作能终止底层 HTTP 请求，不把取消误报为正常完成。
- [ ] 日志、UI 和错误上报中不包含 API Key、Bearer、Cookie、图片 Base64 或 `reasoning.encrypted_content`。

## 8. 与本项目本地测试接口的区别

其他程序若只需调用中转站，直接实现本文的上游协议即可，**不需要**调用本项目的：

```text
POST /api/settings/codex-test-chat
```

该地址只是本程序浏览器测试弹窗到 Next.js 服务端的内部接口。它接收 `keyId` 和本地 `messages`，由服务端读取保存的 Key 后再执行上述上游请求，并把上游 SSE 转换成带诊断信息的本地 SSE。移植到独立程序时，应该在自己的安全后端保存 Key 并直接请求目标中转站。

不要让普通网页前端直接持有或请求中转站 API Key：除了泄露凭据的风险，浏览器还可能受 CORS 限制，且不能可靠设置 `User-Agent` 等受限 Header。Web 应用应让浏览器调用自己的后端，再由后端按本协议访问中转站。

## 9. 重试与兼容性边界

本协议核心的单次调用不内置 SDK 重试，也不自动从 Responses 降级为 Chat Completions。是否重试是调用业务的策略，而不是线协议的一部分：

- 对用户明确取消、请求格式错误、模型不支持、非法 JSON 输出等确定性错误，不应盲目重试。
- 对 408、409、425、429、5xx 或确认的网络短暂中断，可以由业务层设置次数有限、可取消、带退避的重试。
- 当前项目的 GPT 自由视觉单镜 HTML 调用存在一个业务层例外：在首次 502/503/504 或明确的短暂网络/上游故障后，可能额外重试一次；这不是 `streamCodexResponses()` 本身的行为。
- 不应因为第一次 Responses 失败就暗中改成 Chat Completions；协议切换必须是明确的兼容策略，并记录发生过切换。

中转站可能扩展额外事件、忽略 `client_metadata`，或不返回 `[DONE]`。这些均可兼容；真正的成功边界仍是可解析的 `response.completed`。若目标中转站不支持 `reasoning`、`include` 或某个模型，请由接入方明确验证并决定兼容策略，避免在同一次调用中静默篡改请求参数。
